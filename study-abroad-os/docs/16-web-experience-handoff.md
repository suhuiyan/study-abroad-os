# Study Abroad OS — บรีฟพัฒนาเว็บ (ส่งต่อให้ทีมทำงานได้)

อัปเดต: 2026-10-06  
สถานะ: กรอบผลิตภัณฑ์และขอบเขตงาน ไม่ใช่คำยืนยันว่าฟีเจอร์ทั้งหมดสร้างแล้ว

## 1. เป้าหมาย

สร้างเว็บที่เรียบง่ายสำหรับนักเรียนไทยที่สนใจปริญญาตรีในจีน ให้กรอกข้อมูลของตนเอง ค้นหามหาวิทยาลัย/หลักสูตร เข้าใจเหตุผลที่ผลลัพธ์เกี่ยวข้องกับตน อ่านข้อมูลที่จัดระเบียบพร้อมหลักฐาน บันทึกตัวเลือก และติดตามการสมัครได้ นักเรียนต้องค้นหาเองได้เสมอ แม้ยังไม่กรอกโปรไฟล์หรือข้อมูลมหาวิทยาลัยบางช่องยังรอตรวจสอบ

หลักการออกแบบ: หนึ่งหน้าจอมีงานหลักชัดเจน ภาษาง่าย ใช้ได้บนมือถือก่อน แสดงข้อมูลสำคัญก่อนรายละเอียด รองรับย้อนกลับ/แก้ไขได้ ไม่ใช้คะแนนจับคู่ที่อธิบายไม่ได้

## 2. สถานะโค้ดปัจจุบันที่ต้องรักษา

- แอปอยู่ที่ `web/` ใช้ Next.js, React, TypeScript; หน้า UI หลักคือ `web/src/app/page.tsx` และสไตล์ `web/src/app/globals.css`.
- ปัจจุบันมีแท็บสำรวจหลักสูตร ทุน ที่บันทึก แผนสมัคร และโปรไฟล์; มีค้นหา ตัวกรอง รายละเอียดหลักสูตร แหล่งข้อมูล วันที่ตรวจสอบ การบันทึก และงานในแผนสมัครแล้ว
- `web/src/lib/domain.ts` กำหนดรูปแบบ Profile/Program และกฎตรวจคุณสมบัติเบื้องต้น; `web/src/lib/catalog.ts` เป็นรายการเริ่มต้นที่มีแหล่งอ้างอิงและสถานะความเชื่อมั่นรายข้อ
- `GET /api/workspace` คืน `programs` รูปแบบเดียวกันจากตาราง `program` เมื่อมีข้อมูล และใช้ `catalog` เมื่อยังไม่มีรายการ; โปรไฟล์ ที่บันทึก และแผนสมัครผูกกับบัญชีเมื่อฐานข้อมูลพร้อม ส่วน `POST /api/workspace` รองรับการแก้โปรไฟล์ บันทึก และจัดการแผนสมัคร
- พื้นที่ทำงานมีไฟล์ที่เปลี่ยนอยู่ก่อนแล้ว: ตรวจ `git status` และอ่าน diff ที่เกี่ยวข้องก่อนแก้ ห้ามลบหรือเขียนทับงานเดิม
- ข้อมูล discovery ใน `discovery/` เป็นฐานวิจัยแยกต่างหาก ไม่ถือว่ารับสมัครนักศึกษาต่างชาติหรือเปิดรอบแล้วจนกว่าจะตรวจหลักฐานและอนุมัติ

## 3. เส้นทางผู้ใช้ที่ต้องการ

1. **เริ่มต้น:** เสนอแบบกรอกข้อมูลสั้น ๆ ครั้งแรก พร้อมปุ่ม “ข้ามไปค้นหา” สำหรับคนที่อยากสำรวจก่อน ห้ามบังคับสมัครบัญชีก่อนดูข้อมูลสาธารณะ
2. **โปรไฟล์:** เก็บข้อมูลพื้นฐานและการศึกษาเท่าที่จำเป็น เช่น วุฒิ GPA คะแนนภาษา ปีที่ต้องการเข้าเรียน คณะที่สนใจ และงบประมาณ บอกว่าข้อมูลใดไม่จำเป็น/ยังไม่ทราบได้ โปรไฟล์ที่บันทึกต้องกลับมาแก้ได้
3. **ความต้องการ:** ให้เลือกปัจจัยที่นักเรียนใช้ตัดสินใจ เช่น สาขา ภาษาเรียน เมือง งบประมาณ ปีเข้าเรียน และความสนใจทุน ถ้าข้อมูลยังไม่มีในโมเดลหรือฐานข้อมูล ให้ใช้เป็นตัวเลือกค้นหาใน UI โดยไม่อ้างว่าใช้จัดอันดับแล้ว
4. **ผลลัพธ์:** แสดงรายการหลักสูตรหรือเส้นทางรับสมัครที่ตรงกับข้อมูลที่มี ระบุเหตุผลสั้น ๆ ว่า “ตรงด้านใด” และ “ต้องตรวจเพิ่มด้านใด” แยก `ผ่านตามข้อมูลที่ยืนยัน / ยังไม่ทราบ / มีข้อไม่ตรง` ห้ามใช้คำว่า “สมัครได้แน่นอน” หรือแสดงผลจับคู่เป็นการรับรอง
5. **ควบคุมเอง:** ช่องค้นหาและตัวกรองที่มองเห็นง่าย เปลี่ยน/ล้างค่าได้ แสดงจำนวนผลลัพธ์ และมีหน้าว่างพร้อมวิธีแก้ เช่น ล้างตัวกรองหรือค้นหาคำอื่น
6. **รายละเอียด:** จัดข้อมูลเป็นกลุ่มที่อ่านเร็ว: ภาพรวมหลักสูตร, เกณฑ์, ค่าใช้จ่าย/ทุน, รอบและกำหนดการ, เอกสาร, ลิงก์ทางการ, วันที่ตรวจสอบ และสิ่งที่ยังรอตรวจ มีปุ่มบันทึกและเริ่มแผนสมัคร
7. **แผนสมัคร:** แสดงขั้นตอน เอกสาร และสิ่งที่ต้องทำต่อ ผู้ใช้แก้โน้ต/สถานะได้ และมีทางไปเว็บไซต์ทางการเมื่อต้องสมัครจริง

## 4. กฎข้อมูลและการจับคู่

- แหล่งทางการเป็นหลักฐานสำหรับค่าเรียน ทุน เกณฑ์ และวันสมัคร; แสดง URL ต้นทางและวันที่ตรวจสอบใกล้กับข้อมูลสำคัญ
- ถ้าไม่มีหลักฐานที่ตรวจแล้ว ให้แสดง “รอตรวจสอบ”; ถ้าใช้ข้อมูลจำลอง ต้องติดป้าย “ข้อมูลตัวอย่าง” บนรายการและรายละเอียด ห้ามเติมค่าที่คาดเดาให้ดูเหมือนข้อมูลจริง
- ข้อมูลรอบ 2026 ห้ามนำไปแสดงเป็นรอบ 2027 โดยอัตโนมัติ ตรวจปีและรอบก่อนสรุปสถานะเปิด/ปิด
- ใช้ `Program`/`Profile` ใน `domain.ts` เป็นข้อตกลงข้อมูลเดียวระหว่าง UI, `catalog.ts` และ `/api/workspace`; ถ้าต้องเพิ่ม preference ใหม่ ให้ออกแบบ migration และผลต่อข้อมูลเดิมก่อนทำจริง
- เรียงผลลัพธ์ด้วยเกณฑ์ที่บอกผู้ใช้ได้ เริ่มจากสาขา/ภาษา/เมือง/งบประมาณ/ปีที่สนใจเท่าที่ข้อมูลยืนยัน แล้วแสดงเหตุผลของแต่ละรายการ; ข้อมูลไม่ครบต้องเป็น “ยังไม่ทราบ” ไม่ใช่ “ไม่ผ่าน”
- ไม่ประเมินทุนหรือความเทียบเท่าวุฒิจากคำบรรยายทั่วไปหรือจาก AI เพียงอย่างเดียว

## 5. ลำดับงานส่งต่อ

### ระยะ A — หน้าเว็บที่พัฒนาได้ทันที

ปรับประสบการณ์บนโค้ดปัจจุบัน: onboarding โปรไฟล์แบบสั้นและข้ามได้, preference ที่ชัดเจน, รายการผลที่อ่านง่าย, ค้นหา/กรอง/ล้างค่า, รายละเอียดพร้อมแหล่งข้อมูล, สถานะไม่พบผล, การแก้โปรไฟล์ และการใช้งานบนมือถือ รักษาฟีเจอร์เดิมทั้งหมด ไม่แก้ schema/migration/seed เว้นแต่จำเป็นจริงและอธิบายก่อน

### ระยะ B — ช่วยเตรียมใบสมัคร

จัดหน้าข้อมูลและ checklist ให้ผู้ใช้เห็นขั้นตอนสมัครบนเว็บมหาวิทยาลัยอย่างเป็นระบบ เพิ่มพื้นที่ให้ผู้ใช้ตรวจเอกสารหรือคำตอบก่อนส่ง หากใช้ AI ให้ช่วยร่าง/แปล/ตรวจความครบถ้วนของข้อความจากข้อมูลที่ผู้ใช้ยืนยันแล้ว และให้ผู้ใช้แก้ไขก่อนนำไปใช้ ข้อมูลตรงตัว เช่น ชื่อหรือคะแนน ให้ดึงจากโปรไฟล์ที่ผู้ใช้ยืนยัน

### ระยะ C — ช่วยกรอกฟอร์มภายนอก (สำรวจความเป็นไปได้แยกงาน)

เว็บมหาวิทยาลัยยังเป็นผู้รับใบสมัครและแหล่งอ้างอิง เครื่องมือ browser automation อาจช่วยนำข้อมูลไปกรอกในฟอร์มของมหาวิทยาลัยได้ตามเงื่อนไขเว็บนั้น ๆ ต้องจัดการความต่างของฟอร์ม, CAPTCHA, login, OTP, ข้อกำหนดการใช้งาน, การอัปโหลดไฟล์ และการเปลี่ยน UI ให้หยุดและส่งต่อผู้สมัครตรงจุดที่ทำไม่ได้หรือไม่มั่นใจ ผู้สมัครตรวจและกดส่งเอง ระบบต้องบันทึกว่าอะไรกรอกแล้ว อะไรรอตรวจ และขั้นตอนไหนต้องทำเอง `Jev`/browser tooling, harness และ LLM เป็นตัวเลือกเชิงเทคนิคที่ต้องทดลองกับเว็บไซต์จริงก่อนตัดสินใจ ไม่ถือว่าบูรณาการแล้ว

### ระยะ D — ติดตามผลและอีเมล

เริ่มจากให้ผู้สมัครอัปเดตสถานะเองและแนบหลักฐานผลสมัคร ต่อไปอาจเชื่อมกล่องอีเมลด้วยความยินยอมเฉพาะขอบเขตที่จำเป็น หรือให้ผู้ใช้ส่งต่ออีเมลเข้าระบบ ระบบควรแยก “อีเมลทั่วไป”, “ขอเอกสารเพิ่ม”, “ผลสมัคร” และ “ได้รับข้อเสนอ” ก่อนเปลี่ยนสถานะ เมื่อผู้ใช้ยืนยันผลตอบรับหรือมีหลักฐานที่ตรวจได้ จึงแสดงหน้าฉลองความสำเร็จและบันทึกหมุดหมาย ห้ามตีความอีเมลทุกฉบับเป็นการรับเข้า

## 6. ขอบเขต AI และค่าใช้จ่าย

ออกแบบชั้นเรียก LLM ให้เปลี่ยนผู้ให้บริการได้ ใช้เฉพาะงานข้อความที่จำเป็น เลือกรุ่นจากการทดสอบข้อความสมัครภาษาไทย/จีน/อังกฤษจริงที่ลบข้อมูลส่วนตัวแล้ว วัดความถูกต้อง ความเป็นธรรมชาติ รูปแบบผลลัพธ์ เวลา และต้นทุนรวมต่อใบสมัคร ไม่ผูกรุ่นใดเป็นข้อกำหนดถาวร ค่าโมเดลเป็นเพียงส่วนหนึ่งของต้นทุน; browser, การลองใหม่, ที่เก็บข้อมูล และการตรวจโดยคนมีต้นทุนเพิ่ม

## 7. เกณฑ์รับงานระยะ A

- เปิดบนจอมือถือและคอมพิวเตอร์แล้วค้นหา กรอง ล้างตัวกรอง และเปิดรายละเอียดได้โดยไม่มีข้อความหรือปุ่มล้นจอ
- คนไม่ล็อกอินสำรวจข้อมูลได้; คนล็อกอินบันทึก/แก้โปรไฟล์และรายการที่สนใจได้ตามความสามารถปัจจุบัน
- รายละเอียดแสดงแหล่งอ้างอิง วันที่ตรวจ และสถานะ “รอตรวจสอบ”/“ข้อมูลตัวอย่าง” ในจุดที่เกี่ยวข้อง
- ผลจับคู่อธิบายได้ และข้อมูลที่ขาดไม่กลายเป็นข้อสรุปว่าไม่ผ่าน
- ปุ่มและลิงก์หลักใช้งานได้; มีสถานะ loading/error/empty และข้อความช่วยให้ทำต่อได้
- รัน lint, build และการตรวจที่เกี่ยวข้อง รายงานผลจริง พร้อมไฟล์ที่แก้ เหตุผล ข้อจำกัด และรายการที่รอข้อมูลจากฐานข้อมูล

## 8. ข้อความพร้อมส่งให้ผู้พัฒนา

> พัฒนา Study Abroad OS ใน `study-abroad-os/web` ตามบรีฟนี้ โดยทำ **ระยะ A** ให้เสร็จก่อน อ่าน `AGENTS.md`, `PROJECT_STATE.md`, โค้ดหน้า `page.tsx`, `globals.css`, `catalog.ts`, `domain.ts` และ `/api/workspace` แล้วตรวจ Git status/diff ก่อนแก้ รักษาฟีเจอร์เดิมและการเปลี่ยนแปลงที่มีอยู่ ใช้รูปแบบข้อมูลเดียวกันทั้ง catalog และ API ทำ UI แบบ minimal ใช้ได้จริงบนมือถือและคอมพิวเตอร์ แสดงที่มา/วันที่ตรวจ/สถานะความไม่แน่ใจ ห้ามสร้างข้อเท็จจริงเกี่ยวกับมหาวิทยาลัย ทุน ค่าเรียน หรือวันสมัคร ห้ามแก้ฐานข้อมูลโดยพลการ หลังทำงานให้ทดสอบการค้นหา ตัวกรอง รายละเอียด โปรไฟล์ ปุ่มและลิงก์ รัน lint/build และสรุปไฟล์ที่แก้ ผลทดสอบ ข้อจำกัด และสิ่งที่รอเชื่อมฐานข้อมูล ระยะ B–D เป็น roadmap ยังไม่ต้องสร้างในงานนี้
